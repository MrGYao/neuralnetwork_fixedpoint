# 质量保证

本文档定义规范文档生成的质量检查和优化流程。

---

## 生成后检查清单

自动化检查项：

- [ ] **结构完整**：5 层目录均存在
- [ ] **README 存在**：每层都有 README.md
- [ ] **渐进式结构**：每层 README 包含导航
- [ ] **技术栈准确**：solution/TECH_STACK.md 包含识别到的技术
- [ ] **项目类型匹配**：特有文档存在（如桌面应用的 PROCESS.md）
- [ ] **AI 加载指引**：README 包含 AI 加载说明
- [ ] **issues 预填充**：包含至少 3 个引导问题

**检查脚本示例**：

```bash
# 检查结构完整性
for layer in product solution architecture implementation issues; do
  if [ ! -d "spec/$layer" ]; then
    echo "❌ 缺少目录: spec/$layer"
  else
    if [ ! -f "spec/$layer/README.md" ]; then
      echo "❌ 缺少 README: spec/$layer/README.md"
    else
      echo "✅ $layer 结构完整"
    fi
  fi
done
```

## 自动迭代优化

### 检测不满意信号

```
用户输入关键词：
  - "不够详细" / "补充"
  - "不准确" / "错误"
  - "缺少" / "缺失"
  - "重新生成" / "更新"
  - "调整" / "修改"
```

### 自动优化行为

**信号触发后**：

```
不够详细：
  → 识别目标文档（当前讨论的文档）
  → 提供改进选项：
      1. 增加示例（选择示例类型）
      2. 增加细节（选择需详细的部分）
      3. 重新生成（按新模式生成）
  → 执行用户选择
  → 自动更新相关 README
```

**不准确/错误**：

```
不准确：
  → 询问具体哪里不准确
  → 接受用户更正内容
  → 更新文档
  → 检查是否影响其他文档
  → 如有影响，询问是否需要同步更新
```

**缺少/缺失**：

```
缺少：
  → 询问缺少什么内容
  → 评估缺少内容应属于哪层哪文档
  → 补充到对应文档
  → 更新该层 README 导航
```

## 内容质量标准

### 对话记录复杂度分级

**简单**（<10 轮对话）：
- 生成精简版规范
- product/VALUE.md：1 段话
- solution/ARCHITECTURE.md：1 页
- architecture/CORE.md：目录结构 + 简要说明

**中等**（10-50 轮对话）：
- 生成标准版规范
- 包含所有基础文档
- 适当示例和说明

**详细**（>50 轮对话）：
- 生成详细版规范
- Level 3 子目录（如有必要）
- 详细示例和推理过程

### 文档长度指导

| 文档类型 | 推荐长度 | 最大长度 |
|---------|---------|---------|
| README.md | 30-50 行 | 100 行 |
| Level 2 详情文档 | 100-200 行 | 500 行 |
| Level 3 子目录文档 | 50-100 行 | 300 行 |

**超出最大长度时**：
- 考虑拆分为多个文档
- 创建 Level 3 子目录
- 或在 README 中提供摘要

## 渐进式验证

### Level 1 验证（README）

检查项：
- [ ] 包含"核心概要"部分
- [ ] 包含"关键要素"部分（至少 2 个要点）
- [ ] 包含"详细文档导航"部分（表格格式）
- [ ] 包含"AI 加载指引"部分
- [ ] 长度在推荐范围内（30-50 行）

### Level 2 验证（详情文档）

检查项：
- [ ] 包含"核心内容"部分
- [ ] 包含"关键要点"部分（至少 3 个要点）
- [ ] 包含"相关文档"部分（如有相关文档）
- [ ] 结构化呈现（使用标题、列表、代码块）
- [ ] 长度在推荐范围内（100-200 行）

### Level 3 验证（子目录）

检查项：
- [ ] 子目录有 README.md
- [ ] README.md 遵循 Level 1 规范
- [ ] 各子文档 50-100 行
- [ ] 子文档间引用一致

## 错误恢复策略

### 文档生成失败

```
失败场景：
  1. 磁盘空间不足
  2. 权限问题
  3. 依赖 skill 不可用
  
恢复策略：
  1. 检查磁盘空间和权限
  2. 确认 progressive-doc skill 可用
  3. 重试生成
  4. 如仍失败，报告用户并提供手动创建指南
```

### 内容质量不达标

```
不达标场景：
  1. 文档过短（<推荐长度）
  2. 结构不完整（缺少部分）
  3. 内容空洞（无实质内容）
  
恢复策略：
  1. 自动补充内容（基于项目识别）
  2. 如无法自动补充，询问用户
  3. 重新验证
```

## 持续优化

### 用户反馈收集

```
在 issues/README.md 中预填：
  
## 反馈指引
- 如发现文档不准确，请更新对应文档后提交 PR
- 如有改进建议，请在 issues/TODOs.md 中添加
- 如发现缺失内容，请补充并更新 README 导航
```

### 定期优化建议

```
生成后 1 周：
  - 检查 issues/TODOs.md 完成情况
  - 根据实际开发更新 implementation/*.md

生成后 1 月：
  - 回顾架构设计是否仍然准确
  - 更新 solution/TECH_STACK.md（如有技术栈变化）
```

## 使用时机

**步骤 5：验证与优化** 时使用本文档：

1. 执行生成后检查清单
2. 如检查失败，触发错误恢复策略
3. 监听用户反馈，触发自动优化
4. 定期提醒用户优化文档
