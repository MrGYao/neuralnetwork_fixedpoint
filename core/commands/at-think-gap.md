description: Gap 分析与优化建议
agent: plan
---

模板文件位置：`.opencode/commands/auto-task/`

## 用途

分析当前阶段与下一阶段的 gap，输出优化建议，自动保存

## 参数

- $1: task-id（可选，默认从 memory-index 读取）
- $2: phase-number（可选，默认当前阶段 +1）

示例：
/at-think-gap
/at-think-gap task-10
/at-think-gap task-10 2

## 流程

### Step 1: 读取当前状态

执行：读取 auto-task/memory-index.md
提取：

- task_id（如参数 $1 存在，使用 $1）
- current_phase
- target_phase（如参数 $2 存在，使用 $2；否则 current_phase + 1）

### Step 2: 读取下一阶段计划

优先读取：

- auto-task/tasks/task-{id}/task-{id}-plan-phase-{target}.md

如果不存在，读取：

- auto-task/tasks/task-{id}/task-{id}-analysis-overall-plan.md
  提取 Phase {target} 部分

### Step 2.5: 读取上一阶段 summary

如果 current_phase > 0（非第一阶段）：

执行：读取 `auto-task/tasks/task-{id}/summary/task-{id}-plan-phase-{current}-summary.md`

提取：

- 产出物列表（实际产出的文件和内容）
- 验证结果（哪些验证通过，哪些未通过）
- 执行摘要（实际执行情况）

如果 current_phase = 0（第一阶段）：

- 标记：无上一阶段，跳过此步骤

### Step 3: 多维度 Gap 分析

#### 维度列表（5 个维度，无优先级、无时间维度）

1. **范围维度**
   - 对比：下一阶段范围 vs 当前工作状态
   - 识别：范围蔓延、范围缺失、范围重叠

2. **依赖维度**
   - **前置依赖识别方法**：
     - 读取下一阶段计划文件的"具体步骤"章节
     - 识别每个步骤中的前置依赖（显式依赖和隐式依赖）
     - 检查这些依赖是否已满足：
       - 检查上一阶段 summary 中的产出物
       - 检查 memory-index 中的工作历史
       - 检查代码仓库中的实际文件
   - 识别：
     - 依赖缺失：必要的前置条件未满足
     - 依赖冲突：前置条件存在冲突
     - 依赖冗余：不必要的前置依赖

3. **质量维度**
   - 对比：下一阶段验收标准 vs 当前产出质量
   - 识别：质量不足、标准不明确、过度质量

4. **风险维度**
   - 识别：潜在风险点、遗漏点、冲突点、阻塞点

5. **技术维度**（8 个子维度）
   - 工具维度：检查工具是否具备
   - 环境维度：检查开发环境是否满足
   - 技术栈维度：检查技术栈是否匹配
   - 架构维度：检查架构兼容性
   - 规范维度：检查是否符合编码规范
   - 风格维度：检查代码风格是否一致
   - 功能性维度：检查功能实现的正确性
   - 实现维度：检查实现方案的可行性

   **代码方案合适性检查**：
   - 读取下一阶段计划中的代码变更方案
   - 检查方案是否仍然合适：
     - 是否与已完成的代码冲突？
     - 是否有更简单的实现方案？
     - 是否需要调整实现路径？

### Step 3.5: Gap 分类

将识别出的 gap 分为五类：

1. **未满足的依赖**：下一阶段需要但当前未满足的依赖项
2. **已达成的部分**：下一阶段的部分目标已经完成
3. **方向偏差的部分**：当前执行结果与下一阶段计划有偏差
4. **代码实现偏差**：代码实现与计划中的代码方案不一致
5. **环境变化**：开发环境、依赖版本等发生变化

### Step 4: 生成变更点列表

对每个识别的 gap，生成标准化变更点：

格式：

````yaml
## 变更点 {n}: {简短标题}

**类型**: add | modify | delete | reorder

**目标**:
- 文件: {文件路径}
- 位置: {章节名或行号}

**原因**:
{为什么要这个变更}

**详细检查清单**:
- [ ] {检查项1}
- [ ] {检查项2}
...

**变更内容**:
```diff
--- 原内容
+++ 新内容
@@ -行号 +行号 @@
-{删除的行}
+{新增的行}
````

**风险提示**:
{可能的副作用}

**影响范围**:

- 预计影响: {步骤或功能}
- 相关文件: {文件列表}

````

### Step 5: 输出到控制台
**完整输出** Gap 分析报告（YAML frontmatter + Markdown body）

格式：
```yaml
---

current_phase: {n}
target_phase: {n+1}
analysis_time: {时间}
gap_count: {count}

````

### Step 6: 写入临时文件

执行：写入 `.temp/at-think-gap-{task-id}-{phase}.json`

内容：

```json
{
  "task_id": "task-10",
  "current_phase": 1,
  "target_phase": 2,
  "analysis_time": "2026-08-13T14:30:00",
  "gap_count": 3,
  "target_file": "task-10-plan-phase2.md",
  "dimensions": { ... },
  "change_points": [ ... ]
}
```

### Step 7: 自动调用保存命令

执行：`/at-think-gap-save $1 $2`

## 注意事项

- **完整输出**: 不截断，完整展示所有变更点
- **自动保存**: 执行完成后自动调用 at-think-gap-save
- **无副作用**: 不修改任务文件，只生成临时文件和 gap 中间件
- **多 session 安全**: 临时文件名包含 task-id 和 phase，避免冲突
